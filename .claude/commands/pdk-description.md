# /pdk-description — 기능명세서 작성

`$1`=화면ID. `/pdk-screen` 으로 등록한 화면의 **기능명세서**를 대화형으로 작성한다.
UI(와이어프레임)와 아직 짝짓지 않은 요구사항·페이지 컨셉을 **텍스트로 먼저 정리**해 두는 단계다.
결과는 `config/specs.js` 에 기록되고, 상단 바 **기능명세서** 버튼을 누르면 엑셀 양식과 같은 **표**로 보인다.
이후 `/pdk-wireframe` 이 Description 을 쓸 때 이 명세를 끌어다 쓴다.

> 전체 순서: `/pdk-init` → `/pdk-screen` → **`/pdk-description`** → `/pdk-flow` → `/pdk-wireframe` → `/pdk-figma-sync`
>
> 양식 기준: `templates/기능명세서_양식.xlsx` — 컬럼과 작성 방식이 이 커맨드의 규칙과 같다.
> (엑셀 파일을 읽을 필요는 없다. 아래 「행 스키마」가 그 양식을 그대로 옮긴 것이다.)

## 행 스키마 (`config/specs.js` — 엑셀 양식 컬럼과 1:1)

| 엑셀 컬럼 | 필드 | 작성 규칙 |
|---|---|---|
| ID | `id` | `<프로젝트 코드>-FUC-<3자리>`. 프로젝트 전체에서 **이어지는 일련번호** (화면별로 새로 시작하지 않는다) |
| Location 1~6Depth | `location` | 기능 위치 계층 배열. 1Depth 부터 **전체 경로**를 적는다(엑셀처럼 상위 칸을 비우지 않는다 — 병합 표시는 엔진이 한다). 최대 6단계 |
| Page ID | `pageId` | 이 화면ID. 화면이 정해지지 않은 기능이면 `'미정'` |
| Page Name | (없음) | **적지 않는다.** 엔진이 `pageId` 로 `screens.js` 에서 찾아 표시한다 |
| Target | `target` | 사용 대상 (예: `가맹점주`, `일반 회원`) |
| Detail: Content | `content` | 기능명. **짧은 명사구** (예: `주민등록번호 입력`, `등록하기(CTA) 버튼`) |
| Detail: Description | `description` | 상세. 아래 「상세 작성 규칙」 |
| Priority | `priority` | `'High'` / `'Medium'` / `'Low'` 중 하나 |

### 상세(description) 작성 규칙
- **번호를 매긴 여러 줄**로 쓴다: `1. …\n2. …`. 하위 항목은 `  - …`(공백 2칸 + 하이픈).
- 문체는 **"~할 수 있다 / ~한다 / ~보여준다"** (사용자가 할 수 있는 것 + 시스템이 하는 것).
- 담을 것: 동작 · 조건(언제 활성/비활성) · 검증(글자 수, 형식) · 예외(실패 시 메시지) · 정책(제한, 보존 여부).
- 안내 문구는 **큰따옴표로 실제 문장**을 적는다: `"만 14세 미만의 자녀만 등록 가능합니다"`.
- **디자인 묘사(색·크기·위치) 금지.** 그건 `/pdk-figma-sync` 의 영역이다.
- 한 행 = 한 기능. 한 행에 기능 두 개를 섞지 않는다(나중에 Description 과 1:1로 이어 붙이기 쉽다).
- 예:
  ```
  1. 사용자는 자녀의 주민등록번호를 입력할 수 있다.
  2. 주민등록번호 뒷자리는 마스킹(*) 처리한다.
  3. 앞자리 6자리 입력 후 자동으로 뒷자리 입력칸으로 넘어간다.
  ```

## 절차

### 1) 대상 확인
- `config/screens.js` 에서 `$1`(화면ID)로 page 를 찾는다.
  - 없으면 "먼저 `/pdk-screen` 으로 등록하세요"라고 안내하고 중단한다.
  - `$1` 이 없으면 화면ID 를 묻는다. 화면과 무관한 기능만 적고 싶다고 하면 `pageId: '미정'` 으로 진행한다.
- 그 화면의 `label`, `context`, `flow.to`(이동·분기)를 읽어 명세의 출발점으로 삼는다.
- `config/project.js` 에 `prdFile` 이 있으면 `docs/prd/<prdFile>` 을 읽어 **이 화면과 관련된 요구사항**을 참고한다.

### 2) 프로젝트 코드 확인
- `config/project.js` 의 `code` 가 비어 있으면 묻는다 — "기능명세 ID 앞에 붙일 프로젝트 코드(영문 대문자 2~5자, 예: `GFC`)".
- 받은 값을 `project.js` 의 `code` 에 저장한다(필드가 없으면 `name` 아래에 추가). 다른 필드는 건드리지 않는다.

### 3) `config/specs.js` 확인
- 파일이 없으면 PDK 원본과 같은 형식(스키마 주석 + `window.PDK_SPECS = [];`)으로 만든다.
- 이 화면(`pageId === $1`)의 행이 **이미 있으면 「수정 모드」** 로 간다.
- 다음 ID 번호 = 전체 행 중 `-FUC-` 번호의 최댓값 + 1 (3자리, 앞을 0으로 채움).

### 4) 기능 초안 제안 → 대화로 다듬기
- `context`·`flow.to`·PRD 를 근거로 **기능 행 초안을 먼저 표로 제안**한다(빈손으로 묻지 않는다).
  - 진입 조건, 입력 항목, 주요 버튼(CTA)의 활성 조건과 결과, 분기(성공/실패), 빈 상태, 예외 메시지를 빠짐없이 훑는다.
  - `flow.to` 의 각 이동(`via`)은 대개 하나의 기능 행이 된다.
- 제안 표는 `ID | Location | Content | 상세 요약 | Priority` 정도로 간단히 보여주고, 사용자가 **추가·삭제·수정**하게 한다.
- 다음을 확인한다(이미 알면 묻지 않는다):
  1. **Location 계층** — 이 화면 기능들이 어느 메뉴 아래에 있는지 (예: `매출 > 매출 조회`)
  2. **Target** — 사용 대상. 보통 화면 전체에 같으므로 한 번만 묻는다
  3. **Priority** — 기본 `High`, 사용자가 지정한 것만 바꾼다
- 상세는 「상세 작성 규칙」대로 Claude 가 문장으로 정리한다. 사용자가 말한 정책·숫자·문구는 **그대로 살린다**(임의로 바꾸지 않는다).
- 대화 중 다른 화면의 기능이 나오면, 그 화면ID 로 행을 만들되 **이번 확인 목록에 따로 표시**한다.
  화면이 아직 없으면 `pageId: '미정'` 으로 두고, 화면을 만들지는 사용자에게 묻는다(만들면 `pdk-screen.md` 「화면 파일 즉시 생성 규칙」).

### 5) `config/specs.js` 기록
- 확정된 행을 `window.PDK_SPECS` 배열에 추가한다. **기존 행 뒤에, 같은 Location 끼리 붙도록** 넣는다
  (엔진은 배열 순서대로 그리고, 연속된 같은 상위 경로만 병합한다).
- 문자열 안의 줄바꿈은 `\n` 으로, 작은따옴표는 `\'` 로 이스케이프한다.
```js
{ id: 'GFC-FUC-004', location: ['매출', '매출 조회'], pageId: 'SCR-SALE-001',
  target: '가맹점주', content: '조회 조건 설정',
  description: '1. 사용자는 기간·결제수단·승인번호로 거래를 조회할 수 있다.\n2. 기간은 최대 3개월까지 선택할 수 있다.',
  priority: 'High' },
```

### 6) 안내
- 이번에 추가/수정한 행을 `ID · Content · Priority` 로 요약한다. 다른 화면·`미정` 으로 들어간 행은 따로 표시한다.
- 화면을 열고 상단 바 **기능명세서** 버튼을 누르면 표로 확인할 수 있다고 안내한다("이 화면 / 전체" 탭).
- 다음 단계 안내:
  - 다른 화면 명세: `/pdk-description <화면ID>`
  - 명세가 끝나면 **`/pdk-flow [플로우ID] [플로우이름]`** — 화면들을 기능 단위 여정으로 묶는다
  - `/pdk-wireframe <화면ID>` 를 실행하면 이 명세가 **Description 에 자동으로 반영**된다

## 수정 모드

이 화면의 행이 이미 있으면:
- 현재 행을 표(`ID | Location | Content | Priority`)로 보여주고 무엇을 할지 묻는다 — **추가 / 수정 / 삭제 / 순서 변경**.
- **ID 는 바꾸지 않는다.** 행을 지워도 번호를 당겨 채우지 않는다(이미 Description 의 `spec` 이 그 ID 를 가리킬 수 있다).
- 행을 삭제할 때는 `config/screens.js` 의 Description 중 `spec` 이 그 ID 인 항목이 있는지 확인하고,
  있으면 "Description 연결도 끊을까요?"라고 묻는다.

## 주의
- 쓰는 파일은 `config/specs.js` 와 (코드가 비었을 때) `config/project.js` 의 `code` 뿐이다.
  `config/screens.js` 의 `description`(화면 위 hover 라벨)은 **건드리지 않는다** — 그건 `/pdk-wireframe` 이 쓴다.
- 기능명세(specs) ≠ Description:
  - 기능명세 — **무엇을 해야 하는가** (요구사항·정책·예외, 길고 자세하게, UI 와 무관)
  - Description — **화면의 이 요소가 무엇인가** (30자 내외 라벨, UI 요소에 매핑)
- Page Name 을 저장하지 않는다. 화면 이름은 `screens.js` 가 단일 소스다.
